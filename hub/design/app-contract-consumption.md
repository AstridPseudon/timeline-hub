## Minimum accepted closure: consume Runtime §4.1

Runtime published its final `CanonicalDocument` while this mapping was being reviewed. Use that DTO verbatim; no competing App container is needed. It provides the minimum records required for the main editor and popup projections:

```text
CommittedMutation<CommitAccepted>
  receipt.receipt_id                           # accepted publication ID, also for A→A
  data.accepted_revision_id                    # exact parent revision, not latest
  data.canonical_document
    schema_version: 1, project_id, timeline_id
    parent_revision
      revision_id, content_digest
      payload                                 # complete ParentComposition
    shot_revisions[]
      shot_id, revision_id, internal_timeline_revision_id, content_digest
      payload                                 # complete ShotPayload
    internal_timeline_revisions[]
      timeline_id, revision_id, content_digest
      payload                                 # complete TimelineConfig
    dependency_manifest
      shots[]                                 # shot_id, revision_id, internal_timeline_revision_id, content_digest
      internal_timelines[]                    # timeline_id, revision_id, content_digest
      media[]                                 # media_id, content_digest
      documents[]                             # exact retained DocumentPin values
```

Keep all other `CommitAccepted` fields from §4.1: status, base/previous pairs, rebased_onto, document_digest, executed commands, id_map, publisher, provider/compiler versions and optional batch metadata. `parent_revision.revision_id` equals `accepted_revision_id`; the enclosing receipt supplies publication identity. Project scope is on the document, not duplicated into every image. Manifest rows and images must match, with the Runtime-specified sort order; occurrence/clip order remains authored. `document_digest` covers canonical JSON of the entire CanonicalDocument: it has no enclosing publication/actor/storage timestamps, while any authored timestamps inside payloads remain intact and hashed. Each image retains its separate payload digest. App consumes/verifies these rules through generated types and the scoped adapter rather than defining another digest convention.

Minimum **payload content**, already used by App:

- Parent: complete config (output settings, track IDs/order/roles, theme/app/extension values and persisted source bundle), canonical top-level clips, registry and ordered occurrences. An occurrence retains `occurrence_id`, `shot_id`, `shot_revision_id`, placement/start, duration, track, source offset, speed, transform, gain/mute and any authored bindings. Preserve unknown payload fields and explicit null/absence; do not merge divergent legacy config/top-level clip copies.
- Shot: exact internal revision link, dependencies, timing, stable asset/object identities/digests/media types/scopes, and existing audio/text bindings/provenance/generation-input fields when present. Resolve its linked internal image and that image's timeline scope from the verified closure/manifest, never today's shot. Missing or ambiguous links refuse projection; no synthetic scope.
- Internal: complete authored/compiled TimelineConfig, including opaque fields and timing/time maps. Final §4.1 uses this payload directly; adapt main's current `internalPayload.timeline ?? internalPayload` read to that generated form.

The final closure includes reused children and the transitive immutable dependencies needed by the current validator/projection. Empty child arrays are valid without occurrences. A flat config or a list of bare revision IDs cannot hydrate the popup. The ACK can therefore project without a current-head reload, and existing immutable GETs can reconstruct the same closure on reload; no latest-child substitution. Browser asset URLs/caches remain local addresses resolved from the exact registry and authority.

Adapt `runtimeGraphToContract` locally to the prepared-graph shape using `parent_revision` and these child images. Its local graph `schema_version`, derived deep links/output identities and validator `cases` are not additional Runtime wire fields. Canonical authored bytes remain separate from display filtering/time offsets. Runtime final `PreparedCommit` has this one complete closure and the authoritative Recorder; executed commands derive from its records (no separate PreparedCommit.commands). There is no second `publication` payload or null/no-change variant; `rebased_onto`/status are derived by Runtime on acceptance.

Runtime retains exact consumed transcript/config contents under immutable content-addressed DocumentPins; App consumes the snapshot pins/capture contract rather than assuming a mutable Document version remains retrievable. The closure dependency manifest includes those documents; no general Documents history is introduced.

Runtime §5 also closes baseline/bootstrap pins: load exposes `head_revision_id` plus `head_publication_id`; a fresh parent publication has a real receipt/event, while document creation alone is insufficient. An existing head needs verified receipt/event/sequence/closure linkage, with unknown legacy intent conservatively whole-scope. Missing provenance returns `history_unavailable` and leaves data readable but uneditable; App never synthesizes a base. Publication history pages are bounded by their returned head pair and include same-content acceptance edges.

## Exact request and durable local ownership

Persist an outbox record before first transmission, scoped by `(realm_id, authenticated_actor, project_id, timeline_id, durable_owner_id)`. Minimum local contents: accepted base pair/immutable closure reference, exact pending HTTP method and canonical Runtime route path (without discovery origin or door proxy prefix), serialized body and `Idempotency-Key`, the local intent IDs covered by that prefix, ordered unsent builders with their original dependency/basis metadata and created IDs, plus an ownership fence. These are local fields, never a new wire session sequence. A popup records occurrence identity/child pins within its builder metadata under the real parent timeline. Existing `parent:shot:occurrence` keys alone cannot distinguish realms, actors or independent writers.

Local undo can cancel only work that has never been sent. It cannot erase an uncertain in-flight request: resolve that exact request first, then submit a guarded inverse against its accepted publication if the user still wants to undo it. Treat that inverse as dependent unsent intent until its target receipt is known; never replace A with a snapshot or a new key.

One read-write IndexedDB transaction reserves the immutable request, key, allocated entity IDs and covered prefix before any send. On ACK, a transaction matches owner/fence/request key and removes only that prefix while storing its exact accepted pair/closure/receipt; it preserves B even if B was edited or undone during the request. Fence all late completions/errors by the same request/owner generation: a callback for an already-acknowledged prefix cannot regress accepted history or saved/conflict UI. Persistence failure means do not transmit: R4's ephemeral-session fallback would violate crash-safe recovery. Never derive a retry key from a fresh snapshot, randomize created IDs again or infer acceptance from equal head content.

Proposed minimum tab exclusion: a browser exclusive lock per scoped durable outbox, held for its active writer/retry lifecycle, plus a persisted claim generation checked by every IndexedDB write/ACK. A losing tab may inspect pending work but cannot send it or overwrite its suffix. Independent tabs start separate durable owners/keys; copying an opener's sessionStorage is not adoption. Reload/restart enumerates same-realm/same-actor recoverable owners and claims the selected owner under the exclusive lock, advancing the local fence atomically; an older callback cannot clear it. A lock released by a crashed page permits recovery without introducing draft expiry or a time-based lease protocol. If the browser cannot provide safe exclusion/durable storage, keep local work visible and refuse sending rather than silently claim recovery. Exact browser primitive/test details are App implementation work; the correctness boundary is one active owner per outbox, not one tab per timeline.

On Runtime restart, main `client.ts:66–74,285–318` fences changed instances until relaunch. After relaunch, negotiate current compatibility and verify the same realm and authenticated stable actor before claiming/retrying. Canonical path, body, key and actor stay fixed; discovery port, Runtime process instance and rotated credential may change and are not retry identity. Never store bearer secrets in the outbox. A different realm/actor cannot adopt or resubmit uncertain work with a fresh key. Local persisted scope is a recovery hint, never authority.

## Pending A + unsent B + remote C

Let `H0=(R0,P0)` and `S0` be its exact closure. A is a completed gesture, B is newer local intent created while A is uncertain, and C is another author's edit. Pin every state by revision **and** publication; equal revision does not erase a publication edge.

Concrete intent: A places clip X at 5 seconds; while its ACK is lost B intends X at 7 seconds. After exact A recovery, B still means 7, not “move current X another 2” applied to HC. An unrelated C track-label edit must pass on the server; a C change to X's relevant position/read dependency conflicts. Relative B keeps its original read basis. No client expectation rewrite is permitted; the Agent conformance case proves this rule. These are semantic examples, not invented Agent operation arguments.

If B is already a complete independent command proposal on H0, preserve H0 and its recorder expectations; do not change its base to HA just to send it. If B depends on an unaccepted entity from A, wait for A as above. Before any submission a fully dependent gesture batch may instead be built atomically on one accepted base, but A's already reserved bytes cannot grow to include B. If A was never accepted and C advanced first, exact A retry is evaluated/rebased by the server from H0; the returned accepted A image supplies HA for the same original-guard verification; guards are not refreshed from that image. A semantic conflict/refusal leaves dependent B retained; ambiguous transport or `head_busy` keeps the exact A retry pending. Distinguish typed conflict/refusal/authorization/storage/transport states; do not interpret every 409 as overlap or parse prose.
