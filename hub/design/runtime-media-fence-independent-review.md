## Separate reachable publication defect: owner triage

Independently reproduced the incidental `UNIQUE constraint failed: generations.id`
using normal public service operations on current2c4, without a semantic callback
or SQL mutation: settle a real MP4 publication, retry the completed task, register
and claim a replacement executor, then settle that task's original admitted
`generation.publish_v1` effect with the new valid attempt lease and a fresh key.
Both identical bytes and different valid MP4 bytes hit the same error.

`store._apply_settlement_effect` derives the generation ID from task ID/group key
and unconditionally inserts it; retry preserves task/spec and existing catalog
rows. The collision is therefore reachable, not hypothetical and not specific
to equal output bytes. The same derivation/insert and retry reset exist in the
inspected main reference. This is **an unintended retry/publication availability
defect**, not a successful replacement completion or an accepted stale selection.
An exact retry of an already accepted settlement is a different ledger operation.

The private probe confirmed whole SQL/CAS state unchanged across each failed
replacement settlement, original catalog preserved, replacement still
running/unsettled, and original media selection refused. It did not claim a
replacement publication succeeded or encode the failure as desired behavior in
the repository test suite. No product fix was attempted.
