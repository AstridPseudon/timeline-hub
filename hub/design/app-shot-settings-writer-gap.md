## Proven data loss and bounded repair

Before repair: load discarded arbitrary settings keys and nested pair/model fields; saving `{...loaded, prompt: 'Revised'}` replaced the complete raw settings object. It erased unknown data, changed unrelated `negativePrompt: null` to `''`, and materialized previously absent defaults. This was reproduced through the real component callbacks, graph builder, adapter admission and real outgoing `toRuntimePublication` encoder. The name path preserved the same opaque fixture.

Repair is local to `ShotEditorView`: compare the incoming JSON form with the normalized current settings using the existing structural JSON equality helper, overlay only changed root form fields onto the raw settings root, and retain every unchanged raw value. Object key order does not signal a change; array order does. No generic merge/serializer framework or public validation relaxation was added.

When a changed compound field's raw value differs from its normalized view, and the supplied complete value is not the original raw value, the whole save refuses before publication. The error toast says the draft is kept; the existing entity store retains the edited form, original clean snapshot, dirty state and error. This deliberately avoids guessing how to splice opaque pair arrays/model objects. Ordinary representable compound edits and explicit root null/removal continue to work. This guard addresses loss during normalization; it is not a new contract for arbitrary semantic merges or intentional compound replacement.

The snapshot form cannot distinguish an explicit unchanged-value write/clear from an untouched displayed default. This repair cannot supply the recipe's write-intent recording. A native field capture must supply that intent explicitly.
