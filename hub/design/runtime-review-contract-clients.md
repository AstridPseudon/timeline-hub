## Ranked findings

### 1. P1 — A read-only credential can persist project-owned view artifacts (pre-existing)

**Locations:** `runtime_protocol/server.py:585`, `runtime_protocol/service.py:2553`, `runtime_protocol/service.py:2571`, `contract/openapi/workspace-v1.yaml:262`; Python client `packages/python/astrid_runtime_client/generated.py:934`.

**Scenario:** An authenticated actor with only `projects:read` sends `POST /v1/projects/P/timelines/T/views` with `{"formats":["md"]}` and no `Idempotency-Key`. The route requires only read scope, but `create_timeline_view` calls `ingest`, adding the artifact to CAS and associating it with the project. A socket-free probe using the actual `RuntimeHandler._route`, actual `CredentialStore.require`, and actual `RuntimeService` returned 200, made four SQL changes, and created the object file/directory. Neither `projects:write` nor `objects:write` was held. Its internally derived key provides deduplication, but does not supply caller write authority or meet the stated per-write header requirement.

**Impact:** Read authority grants durable project-object mutation and storage consumption. This route is not admitted by the browser door, but is public on the authenticated Runtime listener and both clients expose it. The same handler/service behavior exists at `4bb1d0f7`; this is not an M2 regression.

**Existing tests:** `tests/test_timeline_native_inspection.py::test_markdown_png_custody_and_dedup` explicitly proves persistence/dedup; `::test_daemon_generated_client_without_executor_catalog` exercises the successful API with an owner credential. No existing negative read-only-credential test found. Independently reproduced by the review probe.

**Recommendation:** Either return the view without durable mutation, or require write authority and an explicit idempotency key in server, contract and both clients. Preserve the view behavior.

### 2. P2 — The published contract/clients still advertise 16 unconditionally retired operations

**Locations:** `contract/openapi/workspace-v1.yaml:349`, `:371`, `:398`, `:413`, `:419`, `:430`, `:445`, `:450`, `:456`, and the following shot item/binding operations; `runtime_protocol/server.py:567`, `:588`, `:632`, `:646`; supporting refusal implementations `runtime_protocol/service.py:1610`, `:3110`, `:3352`; Python `packages/python/astrid_runtime_client/generated.py:991`, TypeScript `packages/typescript/src/generated.ts:194`.

**Scenario:** A caller follows the contract and calls `createProjectShot` with a valid project, write credential, object body and idempotency key. OpenAPI advertises 201; both clients expose a successful mutation API; the service always returns 410 `retired_route`. The same discrepancy exists for `updateProjectShot`, `archiveProjectShot`, `recoverProjectShot`, `addShotItem`, `removeShotItem`, `reorderShotItems`, `promoteProjectShotCandidate`, `setProjectShotTextBinding`, `setProjectShotTextBindingById`, `rebindProjectShotTextBinding`, `replaceTimelineClip`, `replaceParentCompositionMedia`, `archiveTimeline`, `recoverTimeline`, and `createTimelineDocument`.

The review probe dispatched **all 16** against the real handler/service with a write credential and key: all returned 410; **none** of those OpenAPI operations declares 410. The nine specifically assigned removals are correctly gone; this finding concerns the remaining surface after the wider M2 writer retirements. `createTimelineDocument` was already retired in the baseline; the other writer retirements are in the reviewed range. The error enum in `contract/schemas/common.json:34` also cannot describe `retired_route` if that common response is used to document them.

**Impact:** Consumers generated from the published contract discover and implement impossible writes; successful contract/client projection tests do not catch the disagreement with dispatch. The hand-written `update_timeline_document` / `updateTimelineDocument` helper also still targets the retired `timeline:` document route; this helper was already broken before the reviewed range and has no in-tree call sites.

**Existing tests:** `tests/test_timeline_shot_authority.py`, `tests/test_timeline_legacy_authority.py`, and `tests/test_timeline_reference_authority.py` prove refusal; `tests/test_client_parity.py` only checks the clients against the stale operation inventory. No test found that checks advertised mutation success against retirement. Review probe verifies each of these 16 endpoints without a socket.

**Recommendation:** Remove the retired public operations/helpers, or explicitly document their compatibility-only 410 behavior and replacement command path. Keep the intentional refusal and existing behavior tests.

### 3. P2 — Restored composition publication omits its eligibility and refusal contract

**Locations:** `contract/openapi/workspace-v1.yaml:343`, `contract/schemas/shot-composition.json:12`; implementation `runtime_protocol/service.py:2760`, `:2768`, `:2775`.

**Scenario:** A client creates a timeline under the installed command provider, reads its head, then follows `publishParentComposition`'s description to publish a complete composition using that head. The handler does not perform a normal successor publication: any tracked head is refused with 409 and `details.reason = timeline_commit_required`. An untracked publication can instead fail with `stale_head`; an apparently headless timeline containing hidden authored content/scoped rows fails with `headless_content_not_empty`. OpenAPI only says “Atomically publish one complete one-level parent composition” and references the generic Conflict response. It contains none of the three discriminators or the tracked/headless eligibility distinction.

**Impact:** The generic 409 status is accurate, but consumers cannot discover when the restored compatibility route is usable or how to distinguish command migration from a head race or hidden-content protection. The new headless-content guard widens this existing documentation gap. The implementation's guards are correct and should remain.

**Existing tests:** `tests/test_timeline_legacy_authority.py::test_http_publish_parent_composition_refuses_tracked_timeline_without_writes`; `tests/test_timeline_headless_overwrite_refused.py::test_empty_parent_over_hidden_nonempty_content_of_a_headless_timeline_is_refused_untouched`, `::test_empty_default_over_authored_headless_shell_is_refused_untouched`, and `::test_genuinely_empty_headless_timeline_still_accepts_expected_head_null`. No contract assertion found for those three reasons. Review probe separately confirmed tracked publication's 409 body.

**Recommendation:** Document the restored route's actual domain and the three 409 reasons. This does not require changing the settled restoration or safety policy.

### 4. P3 — Wrong-project composition publication discloses ownership rather than matching 404 (pre-existing)

**Locations:** handler `runtime_protocol/server.py:573`; supporting service check `runtime_protocol/service.py:2756`.

**Scenario:** Timeline T belongs to A. Submit an otherwise scoped publication at `/v1/projects/B/timelines/T/composition-revisions`, with body project B and a write credential. It returns 409 `{"code":"conflict","message":"timeline belongs to a different project"}`. `GET /v1/projects/B/timelines/T` returns 404 `timeline not found`; the new verified-document reads return identical 404 bodies for a foreign document and a missing document. The publication response distinguishes an existing foreign timeline from one not present there. Independently reproduced.

**Impact:** Inconsistent non-disclosure/ownership behavior across project routes. Credentials currently grant operation scopes globally, not a per-project ACL, so this is **not** evidence that the review bypassed a project-bound credential. This check and message exist unchanged at `4bb1d0f7`.

**Existing tests:** No test found for foreign-owned T through the restored publication route. `tests/test_timeline_authority_door.py::test_authenticated_foreign_owned_resources_are_refused_without_writes_or_disclosure` covers other families only; verified-read tests cover their foreign-project 404s.

**Recommendation:** Use the established project-scoped not-found response for wrong-project timeline identities; preserve genuine stale-head 409 behavior.
