## 3. Explicit decisions to flatten, and reasons

- **Flatten (canonical lane):** `production/review/merge/SHOTS-ONE-COPY-PLAN.md` (22 Oct, plan only). Reason: film-wide data (registry, tracks) was copied into every shot and drifted. Quoted incidents: 16 Oct track copy conflict (`b7b895ad2`), 17 Oct lost layer tracks, 22 Oct `handle`/`source` dropped from RT3-05 (`2f92ff099`, `cb98e249b`). Decision: "Writers stop emitting copies: split writes shots with clips only; registry and tracks go to the film."
- **Flatten (storage):** `a0949881e` and `UNSPLIT-CHAPTERS-PLAN.md`: "The split form stores film-wide data ... once per chapter shot plus the parent ... Every writer must keep N+1 copies in sync." Plan decision: "One stored form. A film is one parent composition with one shot." Status: plan; the migration gate is not done. `almost-ready-no-first-second-v2` still fails flatten (`conflicting asset key 'RT3-05'`) as of 22 Oct.
- **Why the legacy path remains:** `clip-types/runtime.ts:382` says it stays so the editor can inspect legacy managed shot occurrences during canonical adoption. `shotComposition.ts:128` refuses it inside canonical data. The SHOTS-ONE-COPY plan rule is "No flag, no mode" and "No ... read-only legacy shim. Migrate first, then delete" (UNSPLIT:43).
- **Owner tension:** the 16 Oct owner wish for "multiple shots instead of one huge shot" drove the chapters-as-shots form, which the 22 Oct UNSPLIT plan proposes to reverse. Read the owner's 26 Oct decision against this: it keeps multiple shots and makes each shot a layer, which the UNSPLIT plan's "one shot" form does not express.

## 4. Constraints a "shot = nested layer" change must respect

1. **Nesting depth one.** Runtime `shot-composition.json` title and `test_dependency_scope_and_nesting_are_rejected`; canonical `assertSupportedChildClip`. A shot's internal timeline cannot contain occurrences or shot clips. Any nested-layer change must keep the one-level rule or explicitly revise the contract and that test, which is a Runtime schema change.
2. **Clip semantics stay in @banodoco/timeline-schema.** Runtime contract README: nested TimelineConfig is not redefined in Runtime or App. A layer model should not add shot-only clip fields to the shared schema without a schema change.
3. **Shot content is shared by occurrence.** r4 R-14 and `plan.md:20`: "Shot edits apply to this occurrence by default"; scope `content: this-occurrence | shared-shot`. A shot as a layer must not silently edit every occurrence; the scope model in `spec.md:33` applies.
4. **One registry and track set (SHOTS-ONE-COPY).** Shot children must resolve asset and track ids against the film. Shot-local tracks keep the film's track ids (`plate`, `fx`, etc.). Any nested-layer design that gives a shot its own track list reopens the copy-drift class of bugs (16, 17, 22 Oct).
5. **Renderer convention conflict (from CONTEXT.md, verified only in the facts list).** Remotion composition reverses tracks (first = top) while three.js uses the opposite. A shot-as-layer change touches the same convention; both backends would have to agree.
6. **Migration before enforcement.** SHOTS-ONE-COPY and UNSPLIT both say migrate first, then turn on refusals in the same release. Any nested-layer change must not refuse the owner's live film (`almost-ready-no-first-second-v2`, `01M4GGKMHZ3J8V402C8CWSCE95`) before migration.
7. **Draft status.** Both SHOTS-ONE-COPY and UNSPLIT are "Draft 22 Oct. Plan only." They are not decisions and conflict on whether chapters are shots. The owner's 26 Oct decision is the newest and overrides them only if the owner says so; the plans should be updated, not left contradictory.
8. **Legacy nested renderer (`ShotClipSequence`)** already draws a nested TimelineRenderer with a black background. Reusing it would bring black-background and premount behaviour back; check whether the 26 Oct design is meant to replace it.
