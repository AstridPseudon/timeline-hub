The contract is unchanged. A v2 request still requires `api_version`, `project_id`, `timeline_id`, `base_revision_id`, `base_publication_id`, and `commands`, plus the HTTP `Idempotency-Key`. Commands retain `schema_version`, `op`, `version`, `select`, and `args`; `doc.patch` changes retain `op`, `ref`, `path`, `before`, `value`, and applicable `created`. The request retains `label`, `steps` (`id`, `label`, `intent`, `tags`, `command_ordinals`, `patch`, optional `reads`), `merge` (`fields` or `atomic`), optional request `reads`, `dry_run`, `source`, `rationale`, and `group_id`.

Accepted/merged `{data, receipt}` retains both exact `base` and `previous` pairs, accepted revision, `rebased_onto`, full canonical document plus digest, normalized commands and `id_map`, provider/compiler versions, complete authoritative steps/dependencies, merge mode, publisher, and annotations. The receipt retains `receipt_id`, `command_kind`, `idempotency_key`, `request_hash`, `project_id`, `project_seq`, `event_ids`, `result`, and `created_at`, with `receipt.result == data`. Conflict/invalid/refused responses retain the HTTP status, code, message, and `details` (`status`, `reason`, `code`, `path`, `hint`, `suggested_command`, `base`, `current`, `conflicts`). Dry-run preview retains `would_status`, `evaluated_head`, the full candidate/digest/commands/`id_map`/steps/merge mode, and `receipt: null`. The normative executable examples remain C0 §§1 and 4; this document proposes no DTO and no new rule. D62's persisted authentic `recorder_abi` remains authoritative; D47's prohibition on mutable result/history/authority memos remains in force.

## Boundary model

Runtime is the authenticated durable writer: it owns HTTP identity, idempotency replay, exact head CAS, durable history/events, canonical closure authentication, and the accepted receipt. Agent is the semantic producer: it records reads/selections/bindings/created identities, executes commands, constructs patches and inverse records, and supplies the producer capture that Runtime re-authenticates. A row marked “paired” is deliberately not evidence that ownership should move; it means the same rule is represented at both boundaries and must be specified once without weakening either check.

## Proposed shared-spec grouping

The E1 result should be one versioned declarative rule inventory, not a new request/result type. Suggested groups:

1. **Identity and envelope:** route, publisher, request hash, idempotency, exact base/previous pairs, CAS, retry/unknown outcome.
2. **Closure and observations:** aliases, physical refs, revision/digest pins, owner edges, reads/selections, dependency captures, media/text/source manifests.
3. **Patch and execution trace:** absent/null, list identity/order, managed edges/mirrors, command ordinals, step partition, sequential input/output, authoritative effects.
4. **Merge and refusal:** fields/atomic scope, conflict overlap, invalid/refused taxonomy, dry-run no-write semantics.
5. **History and inverse:** authenticated event/record/digest chain, target/step partition, ABA/intervening guards, physical roots, materialization, source rebound, timeline-root restoration.
6. **Allocation and recorder boundary:** created identities, ownership, reservations/no reuse, persisted `recorder_abi`, explicit D62 native-coverage limitation.
7. **Private state:** request-scoped captures/caches, lifecycle, and no mutable cache/memo as authority.

Use canonical JSON/YAML with stable rule IDs, inputs, evaluation boundary, refusal code family, and ownership. The repositories may consume deterministic generated Python tables or a pinned generated module, but neither may import the other's live checkout at runtime. Spec digest and generator version belong in conformance metadata only and must not alter the C0 wire envelope.
