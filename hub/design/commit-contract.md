## 1. Wire operation

`POST /v1/projects/{project_id}/timelines/{timeline_id}/commit`, operationId `commitTimeline`, through main's Runtime handler and local browser door (`/api/runtime/v1/...` for App). Add this exact method/path to `door.WORKSPACE_ROUTES`. Keep main's origin admission, product credential, readiness, framing and project checks. No `/astrid/v1`, gateway, paired relay or new session header. Ordinary clients authenticate with the existing bearer and handshake; the door supplies its product credential. `projects:write` (or main's existing admin authority) is required, including dry runs; immutable public reads require `projects:read`.

Required header: exactly one valid `Idempotency-Key`, using main's validator. Required JSON fields:

```json
{
  "api_version": 1,
  "project_id": "project-id",
  "timeline_id": "timeline-id",
  "base_revision_id": "immutable-parent-revision-id",
  "base_publication_id": "txn-of-the-observed-head",
  "commands": [
    {"schema_version": 1, "op": "clip.move", "version": "registry-operation-version", "select": "parent/clip:clip-id", "args": {}}
  ]
}
```

The example uses Agent's proposed absolute `clip.move` v1 `on` in timeline seconds; the canonical Agent schema/registry owns its semantics. Optional fields: `dry_run: boolean` (default false), `source: {via: cli|python|app|script|sheet, detail?: string}`, `label?: string`, `rationale?: string`, `group_id?: string`. Source/rationale are attribution, never authority. Unknown envelope fields, duplicate JSON keys, non-finite numbers, invalid command envelopes and path/body identity mismatches are refused. Canonical project IDs are required; do not resolve a mutable project selection during retry. One request is one atomic batch and one accepted undo group; `group_id` does not make separately acknowledged transactions atomic. A multi-publication inverse must explicitly list every targeted publication and guard all of them in one transaction; any failed guard rejects the entire inverse. No implicit grouping across requests, including adjacent requests with the same `group_id`. A completed App gesture emits one final batch; command-local group metadata cannot split that batch into independently accepted undo units.

Use the Agent-owned `EditCommand` envelope: required `schema_version: 1`, `op`, `select` (nullable), `args`, and registry operation `version`; retain its `expect`, `bindings`, `created`, `authorship`, `resolved` fields plus command/batch grouping and rationale as the recipe requires. The new schema version is distinct from operation implementation version; frozen R4 lacks this distinction. Runtime validates the versioned envelope and finite JSON, preserves opaque arguments and explicit null/absence, and never interprets edit parameters. The provider validates handler/version/arguments and verifies or regenerates recorder metadata; client-supplied write records cannot authorize a change. Effective versioned defaults and explicit clears are recorded by Agent. No full-document `change.document` fallback. Agent supplies the canonical command schema; Runtime materializes its byte-identical pin at `contract/schemas/edit-command.json` and generated Python/TS types, rather than inventing a second format. M0 source is `ORCH/design/edit-command.schema.json` (`$id=https://astrid.local/schemas/timeline/edit-command.schema.json`); implementation authority moves to Agent `astrid/core/timeline/schema/edit-command.schema.json` under existing package-data rules. See command-schema-handoff.md. Registry/UI annotations remain Agent-owned.

`base_revision_id` names the exact authored/compiled closure seen by the client. `base_publication_id` names the acceptance that selected it as head; it is a Runtime `receipt_id`, not a content digest. Both pins must agree on this project/timeline and accepted history. They remain unchanged on retry and during server rebase. For a new timeline, use its explicit empty bootstrap publication; missing bootstrap/history is a refusal, never an implicit overwrite. Existing-main heads need a one-time, verified baseline history entry (§5); no verified baseline means editing is unavailable for that timeline.

## 2. Responses

| HTTP | Body | Meaning |
| --- | --- | --- |
| 200 | `CommittedMutation` with typed `data: CommitAccepted` | Durable `status: accepted` or `rebased`; exact replay returns this original body. |
| 200 | `{data: CommitPreview, receipt: null}` | Dry run only; `status: preview`, evaluated head pins and candidate, no accepted identity. |
| 409 | Main Error with `details.status: conflict` | Real edit conflict; details include base/current pins and typed conflicts/choices. |
| 409 | Main Error with `details.status: refused` | Identity reuse with changed input, unavailable history/dependency, or exhausted head-race budget. Stable `details.reason` distinguishes them. |
| 400/422 | Main Error, `details.status: refused` where applicable | Framing/envelope error / invalid command, structure, timing or references. |
| 401/403/404 | Main Error | Existing authentication/authorization/not-found rules; do not disclose another project's history. |
| 503 | Main Error, `code: not_ready`, `details.reason: runtime_unavailable` | Provider/runtime unavailable or outcome unknown; retry exact request. Never implies no acceptance. |

`CommitAccepted` and `CommitPreview` have the exact shapes in §4.1. `accepted_publication_id` is **the enclosing `receipt.receipt_id`**; expose that alias in client adapters if useful, without a second receipt format. `receipt.command_kind = timeline.commit`; `receipt.result` is the same accepted data. Preserve all main receipt facts: request hash/key, project sequence range, committed event IDs, created time and receipt ID. No R4 `runtime_receipt`, evidence digest wrapper or toolchain attestation.

Preview returns the same candidate/recorded-command information, provider/compiler versions, base pins and `evaluated_head` pair, but no accepted/publication identity. A preview is not an acceptance token and does not reserve a key. Sending it later as a real edit requires a new key because `dry_run` differs; normal saving never requires preview first. `canonical_document` is the exact accepted candidate even if head advances before readback; use the immutable parent-revision GET and its child pins to reload it, never an unlabelled latest-head read. Provider/compiler versions do not substitute for revision identity.

Conflicts use stable references/paths, kind, base/theirs/ours values with tagged absence, and optional suggested commands. They never contain a partly accepted document. A stale base alone is not a conflict: the provider attempts rebase. Unavailable ancestry or media identity is a refusal/dependency conflict, not proof that two edits overlap. Head contention after the bounded server retry budget reports `reason: head_busy`, retryable with the same request; it is not a semantic clash.

An empty command array is refused. A nonempty edit that writes an unchanged authored value still receives a new receipt/history edge and recorded writes; it may reuse the immutable content revision. Never discard same-value writes with a before/after diff or R4's content-only `no_change` shortcut. This is necessary for later undo guards and publication ABA detection. A genuinely write-free successful command may likewise record an accepted edge with an empty write set; it must not invent changes.

## 3. Retry identity and the durable boundary

Use main's `command_idempotency` ledger, not a second request journal. Within this realm DB, key scope is `(command_kind=timeline.commit, aggregate_id=canonical_json([project_id,timeline_id]), Idempotency-Key)`. Keys should be globally unique client-generated values; session counters and process epochs are not identities. Another publisher reusing the same scoped key is refused by the hash check, not allowed to replay someone else's result.

`request_hash = sha256(canonical_json({operation: invocation.operation, path: invocation.path, publisher: authenticated_actor, request: invocation.body}))`, in main's existing hex hash representation. `Invocation` is defined in §4.1: a canonical Runtime route path (excluding discovery origin and the door's proxy prefix) and the exact parsed submitted body. For `commitTimeline`, that body is the original `CommitRequest`; for main's restore adapter it is the original restore body and the path includes the selected historical revision. Hash before adapter/default normalization. Absence and explicit default/null remain distinct. Reject duplicate keys/non-finite JSON before hashing. JSON property order/whitespace do not matter; command order, explicit clears, IDs, rationale, `dry_run`, source and group do. Never hash bearer bytes, Runtime epoch, handshake session, HTTP request ID or current head. Same actor with a rotated credential can retry after a restart, subject to current authority and compatibility. A changed actor requires reconciliation, not silent resubmission with a new key.

Execution is serialized per scoped key in the realm's single Runtime owner. Use a small owner-local map of ref-counted lock entries (active hash plus lock), with a separate short map guard; no suitable keyed execution helper exists on main. Register waiters before releasing the map guard and remove entries only after the last user exits. An unequal active hash is refused; equal requests wait, then repeat the durable lookup before executing. Never hold the SQLite/store mutex while waiting, running semantic code or writing a response. This is execution exclusion, not another dispatcher or durable journal; the ledger alone survives restart.

Order for a real request:

1. Validate framing/envelope, authenticate and recheck realm/project/timeline authority. Acquire the scoped execution entry outside the store mutex. Under a short store lock, look up the scoped key/hash **before** checking mutable head, current media selection or loading semantic dependencies, including after any wait/earlier optimistic lookup. Found+equal returns the exact durable result/receipt; found+different returns `idempotency_mismatch` and performs no semantic work.
2. Give a detached request and request-scoped port to the fixed Agent provider. It reads the exact base closure and head, applies/records intent once at base, validates and compiles. If head advanced, it rebases that recorded plan, preserving bindings/created IDs; it does not re-run relative gesture input against the new head. Agent owns this algorithm and merge policies.
3. `port.accept(prepared)` opens the sole outer SQLite write transaction (`BEGIN IMMEDIATE`, main store conventions). Repeat key/hash lookup inside it; recheck current authority, mutation admission, expected **revision and publication** head, captured immutable closures and mutable dependency identities/versions, using §4.1's exact retained-input rules. A changed head returns an internal `StaleHead` without writes. The provider retries against a newly observed head at most twice (R4's three attempts total), using the original recorded plan. A publication change with the same content revision must also be examined.
4. Atomically persist internal/shot/parent immutable revisions, consumed input snapshots and their scoped publication links (§4.1), dependency rows, required current projections, new head pair, a publication ancestry edge, the semantic recorder history, timeline/project events, exact accepted data and main receipt/key/hash. Timestamp, receipt ID and project sequence are Runtime-owned. Commit before notifying hooks or producing a success response. Use an internal renderer-free publication primitive in this transaction; do not recursively call public `publish_parent_composition` and create a second logical receipt.
5. Before releasing the scoped entry, reconcile **every** completion against the durable scoped key/hash: success, preview, conflict, refusal, head-budget exhaustion, provider/validation exception and post-commit hook failure. Equal accepted hash always returns the original durable body/receipt, overriding a loser's rejection; different hash always refuses `idempotency_mismatch`. If no row exists, a clean rejection/preview may return; a claimed acceptance without its row is a protocol failure. If ledger readback fails, return 503 unknown outcome and require exact retry, never a definitive rejection. Recheck authority before disclosing an accepted result. Release execution exclusion before response I/O.

Crash before COMMIT leaves no accepted rows/head/receipt; crash after COMMIT or lost response returns the stored body on exact retry, even after other commits advance the head. Concurrent identical requests converge on one receipt/publication; restart consults the ledger, not the lost lock map. M1 Runtime barrier cases `test_commit_duplicate_add_winner_between_lookup_and_execution` and `test_commit_duplicate_move_winner_between_lookup_and_execution` pause the loser after an initial optimistic miss before keyed exclusion, accept the winner, then resume the loser through the mandatory in-lock lookup (never block the winner behind a barrier-held key lock). Both must return the exact winner receipt/body with one history edge/event set and stable created IDs; exercise conflict/refusal/head_busy/exception completion reconciliation, changed-hash refusal and restart readback too.

Retain `timeline.commit` replay results and semantic history indefinitely for this milestone. Main's generic 24-hour result expiration/pruning and `command_result(created_at=...)` must explicitly exclude this kind in **both** online and offline paths, including receipt reconstruction. This is a deliberate narrow change required by crash-safe outboxes and undo; retention/purge is deferred. Later lossless compaction may reconstruct only from immutable accepted records, with byte-equivalent JSON data/receipt, never current head, media catalog, provider execution or scene evaluation. A missing/corrupt accepted record fails closed; never rerun a known key.

Rejected semantic requests and dry runs reserve no key, revision, event or sequence. Exact retries of an unaccepted request may reevaluate against a newer head; only accepted results are frozen. Changing a refused/conflicted proposal uses a new key. Transport failures are ambiguous until the original request is resolved.

App/CLI/Python outboxes durably store realm/project/timeline, stable publisher, durable local owner/tab fence, canonical route path, exact body/key and ordered local suffix **before** first transmission. On disconnect/restart, negotiate the current Runtime, verify the same realm and actor, and retransmit the exact in-flight request before submitting suffix edits. Discovery origin/TCP port and credential bytes may change after explicit reconnect/relaunch; realm, actor, canonical path, body and key remain fixed. A stored old TCP endpoint is not semantic request identity. Preserve main's changed-instance fence until explicit reconnect/relaunch; a new process instance must not allocate a replacement request. Do not replace the in-flight base, commands, pins or key, run a client semantic rebase, infer success from similar head content, or allocate replacement entity IDs. Acceptance removes only the acknowledged prefix. Dependent unsent suffix commands wait until that prefix is acknowledged, then bind a fresh request to its exact accepted head pair while retaining every original value/identity/read/selection guard and created-ID dependency. Provider verifies those guards before it records/rebases the submitted command. Guard failure is a real conflict; a rejected predecessor leaves dependent work conflicted and retained. Equal-state ABA is not a conflict for this handoff (PLAN Decisions log); this does not relax accepted-undo write-history checks. No basis field or client semantic rebase is introduced. Reconcile the accepted document while preserving the suffix's original stable references, values, reads and selection basis; `id_map` is identity-only and must not rewrite the suffix; never relabel an old whole-document snapshot as current. Submit the suffix with fresh request identities only when its dependencies can be bound to an accepted base, otherwise retain it for conflict resolution. App owns local preview reconciliation; server owns semantic rebase. A renderer/preview being unavailable has no bearing on retry.

## 4. Provider composition and scoped reads

Main at `8c1830d` has **no timeline provider ABI**: no `runtime_protocol/timeline_commit.py`, `RuntimeCommitPort`, provider factory registration or interface-version check. Frozen R4 adds those and its scene-dependent v1; it is not an API on main. Therefore the initial slim ABI is **1**, with exact current generated Runtime `SCHEMA_DIGEST` equality and the signatures below. The new commit schemas change that digest, so frozen R4 is incompatible despite sharing the integer 1; its request/prepared DTOs and required port methods also differ from this contract. No v2 is needed.

Startup loads only the installed fixed `astrid.sdk.timeline.commit.create_runtime_commit_service()` for the trusted Astrid authoring profile. The zero-argument factory returns a provider with `provider_id = "astrid-v1"`, exact integer `interface_version = 1`, `contract_digest = runtime_protocol.contract_metadata.SCHEMA_DIGEST`, and synchronous `commit(context, port)` as below. Validate identity, digest, version and method call signature before authoring readiness; registration is startup-only. No scene methods or scene-required capability participate. Missing/incompatible selected provider fails authoring startup with an actionable error, without fallback publication. Neutral Runtime startup does not import Agent and serves commit as 503 unavailable. Durable readback uses Runtime records, not semantic execution; selected-profile compatibility failure still prevents startup.

### 4.1 Authoritative DTOs and synchronous port (ABI 1)

This is the one detached value contract, to be materialized in Runtime `contract/schemas/timeline-commit.json` and generated Python/TS DTOs. Notation: `ID` is a nonempty string, `Digest` is `sha256:<64 lowercase hex>`, `JSON` is finite JSON, `Object` is a JSON object, `?` means optional and absence differs from null. Objects are closed except canonical document payloads and schema-owned extension values. `EditCommand`, `AgentCommandBatch` (the schema's `CommandBatch` array) and the semantic leaf types prefixed `Agent` below are references to Agent's pinned schema, not independently maintained Runtime schemas; their authoritative M0 artifact and packaged projection are defined in command-schema-handoff.md and pinned below. All arrays preserve semantic order unless explicitly sorted below.

`MutationReceipt` aliases main OpenAPI `CommittedMutation/properties/receipt` unchanged, and `CommittedMutation<T>` is `{data: T, receipt: MutationReceipt}`. `ParentComposition`, `ShotPayload` and `RawTimelinePayload` reuse main `shot-composition.json` definitions; the pinned compiled `TimelineConfig` remains unchanged and applies only to compatible compiled/presentation values (see the dated approved schema correction below); `Document` reuses `document.json`. Each image is the timestamp-free immutable GET payload plus its exact identity/digest, with project scope on the enclosing document. Parent payload includes complete config, registry, ordinary clips and ordered occurrences; shots include all metadata/assets/audio/text bindings and the exact internal revision link; internal payload includes all authored/compiled fields. Unknown siblings and namespaced fields survive intact. Unique shots sort by `(shot_id, revision_id)`, internals by `(timeline_id, revision_id)`, manifest rows likewise, media by digest and document pins by `(document_id, version, content_digest)`; occurrence/clip order is unchanged. Verify payload SHA-256 using main `util.canonical_json`, all identity links and manifest equality. `document_digest` hashes canonical JSON of the **whole CanonicalDocument**; it has no enclosing publication, storage timestamps or actor, and opaque authored timestamps inside payloads are preserved and hashed; it is distinct from parent `content_digest`. This closes main App's `runtimeGraphToContract` / rows/config/popup projections without a latest-child read or an R4 `project/primary_timeline` graph on the wire. Timeline display metadata outside these immutable payloads is a separately labelled mutable read, never acceptance proof.

`PreparedCommit.canonical_document` is the complete resulting closure, including reused children. There is no second `publication` payload or null/no-change variant: Runtime derives inserts/reuses and projections from this closure, verifies existing IDs have identical bytes and dependency manifests, and sets accepted revision to `parent_revision.revision_id`. Changed retained input pins require a new closure revision even if authored payload bytes match; same-content revision reuse is valid only for the identical full dependency closure. `PreparedCommit` has no independent commands payload: `records.commands[].command` is the sole executed-command representation. Records have contiguous zero-based execution ordinals; nested calls use Agent's recorded execution order. Runtime derives `Candidate.commands`, accepted/preview commands and persisted response projections from those records. `CommitRequest.commands` remains the external Agent-owned `CommandBatch`; normalization/expansion can change its executed projection, never the original Invocation/hash. `id_map` contains identity pairs only (or is empty); any concrete command needing remapping requires a coordinated schema/consumer change first, not speculative rewriting. Each record retains direct unchanged writes, reads, membership/order, bindings, created IDs, dependencies and compiler consequences separately. `AgentState` is exactly `{state: absent}` or `{state: present, value: JSON}`. Agent owns token/reference semantics, leaf schemas and event vocabulary/payload validation; Runtime owns these envelopes, checks ordinal/reference/schema consistency and persists them unchanged. `undo_of` explicitly lists all target publications (empty for ordinary edits); `restored_from` is null except a historical replacement. Batch source/label/rationale/group come only from captured request metadata, command metadata from the schema; no `reason` alias for rationale. Failure `details.reason` remains a machine error discriminator. For sheets use `source.via = sheet`. At provider ingress, after preserving the original Invocation/hash, normalize legacy `expect`/`authorship` target/property strings once using Agent's canonical parser into entity references and token-array paths. Verify ORIGINAL submitted guards before deriving recorder state; retain detached normalized guards through execution/rebase/inverse. Numeric path tokens require container-type reads; quoted `::` is data and ambiguous entity delimiters refuse (command-schema-handoff.md). Runtime persists normalized recorder leaves unchanged; neither history nor adapters reparses legacy paths or invents a second recorder. The canonical command string-map wire fields and Agent-owned inverse/restore arguments remain unchanged.

Domain events are ordered registered semantic facts referencing an executed command, not a second snapshot writer. Agent supplies the registered kind/payload schema; Runtime checks it and assigns event IDs, stream/project sequence, publisher, receipt linkage and timestamps. Provider-supplied payloads cannot override those fields or carry another whole-document mutation. Runtime adds the canonical publication transition event from captured head/candidate; even an unchanged-value acceptance gets this edge. `status` and `rebased_onto` are Runtime-derived: accepted/null iff `expected_head` equals the request's base pair; otherwise rebased/expected_head. Provider cannot supply a receipt, actor, acceptance identity or changed request pins.

`preview`/`accept` share candidate and recorder validation; only `accept` persists. All calls are synchronous, detached and bound to `CommitContext`; publisher is main authenticated `identity["actor"]`. Runtime retains credential/admission handles and captured read dependencies privately, revalidating them at accept. `CommitRejected` maps to §2's existing Error body (`http_status` is transport metadata); failures from reads/validation return no partial candidate. `StaleHead` rolls back everything and is consumed by the provider, never serialized as an outcome; at most three attempts reuse the original recorded plan and IDs, then return `head_busy`. A restore head race instead returns `stale_head` immediately, without rebase. In dry run `accept` raises `CommitRejected` with reason `dry_run_accept`; the provider uses `port.preview(prepared)` against its verified expected head. History authorizes only actual ancestor records. A request cannot smuggle a foreign project into source/restore/inverse references.

Rejection, dry run or pre-COMMIT crash persists no snapshots/links; a post-COMMIT crash retains them with the accepted result. Retain linked inputs with accepted history; include them in existing backup/integrity checks and protect them from generic pruning. No new public history/read endpoint, retention admin or scene evaluation.

## 5. History, inverse, restore and revision reads

Runtime is the only accepted history. Persist the provider's versioned executed commands, writes **including unchanged writes**, tagged prior values, read/selection membership/order expectations, bound references, created IDs, dependencies and undo linkage with each receipt edge. Keep authored state and derived timing distinguishable. A plain JSON diff or content digest cannot replace this recorder. Records are semantic history, not R4 evidence/handback decoration. Provider semantics determine what a write means; Runtime guarantees its immutable association with the accepted publication and atomic head transition.

Each edge records `publication_id = receipt_id`, accepted revision, previous publication/revision, publisher/source/group/rationale, and optional `undo_of` / `restored_from`. Same-content publications remain distinct. Provider scans all intervening edges before rebase/inverse, including writes that changed A→B→A or wrote A→A. Missing history or an old writer with unknown write intent is a dependency conflict, never presumed disjoint. Whole-document legacy writes must be represented conservatively as touching their entire authored scope until removed.

Undo is a **new** commit containing Agent's guarded `timeline.inverse` version `"1"`, `select:null`, `args:{publications:[receipt_id,...]}`: unique explicit targets in oldest-to-newest accepted order, one target represented by a one-item list. Provider reconstructs the inverse from Runtime history and checks intervening writes, references to created entities, membership/order assumptions and structural dependencies; client-provided inverse JSON is not trusted as history. Restore authored state exactly (opaque fields, explicit absence, occurrence isolation, source bindings), then recompile derived timing. It may pass disjoint later edits; it refuses overlap/dependency/ABA. Redo is another guarded reversing edit of the undo, with a new key and accepted edge. No head rewind and no durable client inverse stack as a competing authority.

Bootstrap/baseline verification is Runtime-owned and uses main's existing ledger, not provider-invented provenance:

- A fresh timeline first gets a canonical empty parent closure through the renderer-free main publication primitive, with a real `CommittedMutation` receipt and its `parent.composition.published` event. Main's current `timeline.document.created` receipt alone only proves internal/document creation; it is not proof of a published parent head. Initial parent publication must add the publication event/receipt and bootstrap edge before exposing an editable base (or do so in an extended atomic create transaction). Insert the initial history edge/head pair in that transaction, `intent: bootstrap`, `previous: null`, `records: null`; its receipt ID is the explicit base publication. A null head, sentinel string, revision digest or fabricated receipt is never an editable base.
- For an existing timeline under a write transaction, run main's revision/event-chain integrity checks (including complete dependency rows, project ownership, canonical payload digests and parent→shot→internal pins). Find the latest publication **event in verified stream/receipt sequence order**, not the latest row with matching content. Pair it one-to-one with a `command_idempotency` row's event IDs and non-null `txn_id` receipt ID. Require project/timeline, command/result or compacted-marker identity, old/new heads, digest, manifest and receipt project sequence linkage to agree, and prove this event selected the stored current head with no later unaccounted publication/write. Follow earlier verified receipt/event links where available; when older ancestry is unprovable, start a baseline boundary (`previous: null`) at the verified current publication. Retain its existing receipt ID, original receipt facts and all needed receipt/event/closure rows; never rerun main's scene-dependent `_publication_replay_result` to verify it. A compacted record can be checked structurally using its stored parent/event IDs and manifest hash plus immutable rows; an expired marker alone without sufficient paired facts is not proof.
- Imported legacy edges have `intent: legacy_unknown`, `records: null`, and unknown publisher/version as null where unauthenticated. Treat them as a whole-authored-timeline write for overlap checks; never invent recorder intent from a diff. They can provide a new edit's exact base but cannot themselves be inverted from guessed intent. An inverse/rebase needing a path through unknown intent or beyond the baseline refuses `history_unavailable` (or an explicit dependency conflict). During M1 migration, any still-admitted legacy writer must append such an edge atomically, including same-content writes; M2 closes external canonical legacy writers as enumerated below. An untracked writer invalidates the baseline.
- If a current publication cannot be verified, leave that timeline read-only to the new commit/restore path and return 409 refusal `history_unavailable`; leave existing bytes untouched and expose the integrity reason. Do not synthesize a receipt/event, label corrupt data a fresh empty timeline, or accept a revision-only guard. Recovery is explicit repair of existing provenance or an authorized import into a **new** timeline with a real bootstrap receipt, not an automatic overwrite. Baseline installation is idempotent: compare the stored head and event/receipt pair in the same transaction before publishing its pin.

**Early owner's-film feasibility (M1).** Before widening editing coverage, Runtime runs the baseline checks above on an orchestrator-provided duplicate or read-only snapshot of the owner's film, with its paired realm DB/CAS, project/timeline IDs and receipt/event data. Request the path from the orchestrator if unavailable and report that input blocker immediately; do not defer this check to M4 or claim a fixture proves film compatibility. Read-only verification performs no baseline installation; any installation/edit test uses the duplicate only. Check every used timeline's current head, full child/media/transcript/config closure, canonical digests, source/project authority, event-chain order and one-to-one receipt/sequence/manifest linkage; detect later direct writes and expired/compacted records lacking proof. Report the verified publication/baseline boundary or the exact missing/corrupt facts and required explicit migration/repair early. Do not invent provenance or alter the original film. M4's owner demonstration remains a separate gate. This design task accesses no film.
