# E3 custody audit — one-writer threat-to-safeguard inventory

**Status:** D81 / E-PLAN author-approved design only; non-gating. Luna default; Sol review is a dependent follow-up. This artifact records reviewable recommendations and does not implement them.

## Scope and settled contract

This is the E3 audit requested by PLAN §3, R1/R2/R2r and C0 §§1–7. The settled model is one authenticated Runtime writer, with Agent supplying semantic execution/authoritative captures and App persisting and transmitting exact intent. I did not alter the integration worktrees, the C0 wire contract, the Runtime/Agent/App source, or any test.

The following remain unchanged and are not candidates for pruning:

- Full v2 request/reply: `api_version`, `project_id`, `timeline_id`, `base_revision_id`, `base_publication_id`, `commands`, HTTP `Idempotency-Key`; command `schema_version`/`op`/`version`/`select`/`args`; `doc.patch` changes with `op`/`ref`/`path`/`before`/`value` and applicable `created`; `label`; complete `steps`; `merge`; optional request `reads` and `dry_run`; `source`/`rationale`/`group_id`.
- Accepted/merged `{data, receipt}` and the C0 complete data/receipt fields, including exact base and previous pairs, accepted revision, `rebased_onto`, canonical document and digest, normalized commands/id map, provider/compiler versions, authoritative steps/dependencies, merge mode, publisher, annotations, receipt result equality, and event metadata.
- Failure details (`status`, `reason`, `code`, `path`, `hint`, `suggested_command`, `base`, `current`, `conflicts`) and dry-run preview (`would_status`, evaluated head, candidate/digest, commands, id map, steps, merge mode, `receipt: null`).
- D62 persisted `recorder_abi` and D47’s prohibition on a mutable result/history/authority memo. C0’s authenticated history is the acceptance authority; this audit introduces no DTO or new rule.

### Decision summary

No product custody safeguard in the table qualifies for removal. The sole-writer fact justifies removing competing write authorities and simplifying caller-side preflight/evidence claims; it does **not** justify removing physical identity, alias ambiguity, full capture coverage/order, allocation/ABA, receipt/history authenticity, or inverse guards. The `ASTRID_RUNTIME_CUSTODY_*` controls remain strict HARNESS controls under D64/D66 and must not be used as a substitute for PRODUCT authorization/receipt/binding custody. “Provider/source provenance” is likewise separate: source/artifact identity helps prove which process ran, while Runtime’s authenticated receipt/history proves what product mutation was accepted.

## Concrete migration and proving order

1. Freeze C0 §§1–7, D62 recorder ABI, D47 immutable receipt/history rules, and the no-new-DTO decision.
2. Keep the current one-writer route and App outbox/retirement path. Treat any client alias/occupancy preflight as advisory only after conformance evidence; do not remove its tests first.
3. Replay accepted records through Runtime and Agent with exact and mutated inputs: ambiguous alias, unrelated successor, changed physical digest, missing binding, changed step order, missing read/dependency, forged provider-only effect, and changed request hash. Require the specified refusal shapes and zero writes.
4. Prove custody invariants: deleted ID cannot be newly allocated; inverse restores only original allocation provenance; source→fork→source retains the original pin; A→B→A is an inverse conflict; foreign owner/edge and catalog ABA are refused.
5. Prove receipt/history invariants: lost ACK exact replay, duplicate key with changed body, event/metadata/ABI tamper, missing ancestry, head CAS race, and restart after acceptance. Keep receipt `result == data` and dry-run `receipt: null`.
6. Prove the mounted App journey (outbox, reconnect, reload, guarded undo), then separately run harness custody/source tests. Do not combine a harness green result with a product authorization claim.
7. Sol reviews this audit. Only after that review should implementation be dispatched; this document itself is non-gating and contains no behavioral PASS claim.
