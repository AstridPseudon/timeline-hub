My top three changes:

1. **Make §13 a defined consolidation milestone, and settle its hardest design question before M4 finishes.** Keeping the TS executor through M4 is correct. Deleting it afterward is not just swapping in server calls: each queued edit’s `after` state becomes the basis for the next edit ([commitSession.ts:411](/home/user/work/app/src/tools/video-editor/commands/commitSession.ts:411)). WP5’s generic adapter also relies on local exact replay.

   Specify how dependent edits, original guards, offline chaining, restart recovery and exact retry survive removal. A local “under 50 ms” measurement proves none of that. Use a small design spike covering split → trim with a lost acknowledgement and restart, plus realistic remote delay. The predictor must never become the authority for guards or accepted state. If preserving the behavior requires shared executable semantics, decide that explicitly rather than discovering it halfway through deletion. Existing dry-run support does not solve offline execution.

2. **Make the final simplification measurable by ownership, not line count.** One Python provider, one command meaning, one authoritative history, one shared evaluator, and no independently maintained copies of rendering rules. §16 currently turns the renderer replacement into a “decision”; that does not guarantee the hand-port disappears.

   Identify which App code is legitimate host integration and which duplicates Composition behavior. Retain the former; consolidate the latter before M5. Do not rewrite working adapters merely to achieve “one renderer” or +15k lines. Preserve useful behavioral tests when deleting duplicate implementations; “most fixtures disappear” is not an acceptance criterion.

3. **Replace the accumulated amendments with one executable scope and sequence.** Use: **M4 delivery and stop → required consolidation → renewed gates and ZIP → separately authorized M5**. Cloud implementation can remain later; its architecture decisions should inform consolidation now.

   Specify a proxy path that actually reaches the loopback-only door and satisfies its Host/Origin checks ([door.py:528](/home/user/work/runtime/runtime_protocol/door.py:528)), with Agent and its provider available beside Runtime. Keep normal SQLite, locking and backups. Drop Turso-driven portability work and the extra evaluator harness unless they solve a demonstrated present problem. A diagnostic fallback is not a passed gate.
